# Accessibility

What has been audited, what was fixed, and how to check the rest by hand on
a device. Automated coverage lives in `mobile/__tests__/contrast.test.ts`,
`mobile/__tests__/announcements.test.tsx` and `mobile/__tests__/hero-ring.test.tsx`;
run them with `npx jest contrast announcements hero-ring` from `mobile/`.

## 1. Font scale at 200%

**Audited.** Grepped for `numberOfLines` across `app/` and `components/` and
checked each real usage against what happens when the system text size is
doubled:

- `Hero` (`components/ui/Hero.tsx`) is the one place a layout genuinely
  cannot reflow — a headline number wrapping to a second line looks broken,
  not accessible. It already measures its own box on layout and factors the
  *system* `fontScale` (from `useWindowDimensions()`) into whether the value
  fits, stepping down through 64 → 52 → 44pt before it would ever clip or
  wrap. This means it degrades by getting smaller, never by cutting text off,
  and does not need `maxFontSizeMultiplier` — capping the scale there would
  make the app's one headline figure the one piece of text that *doesn't*
  respect the user's chosen size.
- `Chip`, `Select`'s row label, `history.tsx`'s dish name (compact row) and
  most of the app render text with no `numberOfLines` at all and let the row
  grow — this is the general rule the design guide already enforces
  ("a label either fits or wraps; it never truncates").
- Two places still cap lines: the photo meal row's dish name
  (`history.tsx`, `numberOfLines={2}`, overlaid on the photo itself, where a
  third line would run off the image) and the screen header title
  (`components/ui/Screen.tsx`, `numberOfLines={1}`). Neither sets
  `allowFontScaling={false}` or a `maxFontSizeMultiplier`, so at 200% they
  still scale — they just also still truncate past two/one line(s). This is
  a real, acceptable-but-not-perfect tradeoff (a caption over a photo, and a
  nav bar title) rather than an oversight; revisiting it would mean either
  a taller photo caption area or a header that can grow, both layout changes
  out of scope here.

**Fixed this pass:** nothing — the audit did not find a control that fails
to keep its 48dp target at large text (Button, ListRow and Dialog's actions
all size from `minHeight`/`padding` tokens, not from the label's own
measured height, so a taller label does not shrink the tap target).

**Manual check (do this on a real device before shipping a release):**

1. iOS: Settings → Accessibility → Display & Text Size → Larger Text → drag
   to the far right (or enable "Larger Accessibility Sizes" first for the
   true 200% range). Android: Settings → Display → Font size → Largest, and
   separately Display size → Largest.
2. Walk every tab (Dashboard, Log, History, Streaks, Profile) plus Login,
   Register, Forgot password, and one Dialog (Profile → Goal) and one Field
   error (Login with a wrong password).
3. Confirm: no text is visually cut off mid-word without an intentional
   `numberOfLines` boundary; every button and row is still comfortably
   tappable; the Hero figure on Dashboard and Streaks never wraps.

## 2. Chart and icon-only control labels

**Audited and fixed.** `CalorieBars` (`components/CalorieBars.tsx`) already
collapsed its 14 bars into one spoken summary (`accessible` +
`accessibilityLabel` naming the day count, the junk percentage and the
tallest bar). `Ring` (`components/ui/Ring.tsx`), the dashboard's calorie
meter, had none — an SVG announces nothing on its own, so a screen reader
had only whatever `Text` happened to be nested inside it to go on.

Fixed: `Ring` now takes an `accessibilityLabel` prop and, whenever it has a
target to be a progress bar for, groups itself with
`accessibilityRole="progressbar"` and `accessibilityValue={{ min, max, now
}}` carrying the real numbers. The dashboard passes a label stating the net
figure, the target, and the same "over by" / "left" wording the status line
already prints — see `mobile/__tests__/hero-ring.test.tsx`.

The month-over-month trend card (`TrendCard` in `app/(tabs)/index.tsx`) is a
table of real `Text` rows, not a chart — nothing extra needed there. The
streaks screen's flame is the platform Ionicons glyph plus a plain number;
also nothing extra needed.

Icon-only buttons: audited every `<Icon` usage in `app/` and `components/`.
Every one that is itself the tappable control already carries
`accessibilityRole="button"` and a real `accessibilityLabel` on its
wrapping `Pressable` (profile picture edit badge, password reveal/conceal,
map notice dismiss, Select's clear/close buttons, the raised tab bar log
button). Icons that sit *inside* an already-labelled row (`ListRow`'s
trailing chevron, `Button`'s leading icon, `Chip`'s check mark) are
correctly left unlabelled — they are decorative once the row/button/chip
around them is.

## 3. Reduced motion

**Audited.** Grepped for React Native's own `Animated`, `LayoutAnimation`
and any hand-rolled `setTimeout`-driven motion, since Reanimated's own
tokens (`theme/motion.ts`) already set `reduceMotion: ReduceMotion.System`
on every config and are covered by `mobile/__tests__/motion.test.tsx`.

- No usage of RN's `Animated` API or `LayoutAnimation` anywhere in
  `app/` or `components/` — every animated value in the app goes through
  Reanimated's `useSharedValue`/`withTiming`/`withSpring`, all of which
  reference `quick`, `press`, or `celebrate` from `theme/motion.ts`.
- The one `setTimeout` outside a debounce hook is `history.tsx`'s
  `REFINED_TAG_MS` — it only controls *how long the "Refined" tag stays
  visible before disappearing*, not how it moves. The fade itself is
  `withTiming(1, quick)`, which already respects the system setting.

No fixes needed here.

## 4. Contrast: disabled, pressed, error, placeholder

**Extended `contrast.test.ts` this pass**, and found two real bugs while
doing it:

- **Pressed state was never measured at all.** `Button`'s
  `opacity: pressed ? 0.82 : 1` faded light theme's secondary button outline
  to 2.66:1 against the page and the primary button's label to 4.22:1 on its
  own fill — both under WCAG's floor — while every existing case in the file
  only ever checked the resting (unpressed) state. Fixed: raised to `0.9`,
  the least fade that clears both (see the comment in `Button.tsx` for the
  exact numbers).
- **Soft status fills were measured wrong.** `dangerSoft` and `successSoft`
  are translucent RGBA tokens; comparing text against the raw token ignores
  its alpha entirely (the same category of bug the file's own docblock
  already describes). The diary's "Refined" tag printed in
  `colors.success` on `colors.successSoft`, which measures 4.19:1 once
  actually composited over the card behind it — under the floor. Fixed: the
  tag now prints in `colors.text` and lets the tint alone carry the status
  colour, the same rule the app already applies everywhere else ("never
  colour alone").

Disabled state (`disabledFill`/`disabledInk`) and error text
(`danger` on `bg`/`surface`, plus the new `dangerSoft` case) were already
covered or are now covered. Placeholder text got its own named case
(`muted` on `surfaceAlt`, the input fill) rather than relying on the reader
to notice it is the same pairing as "muted text on a raised fill".

**Not covered by an automated test:** every other Pressable's own
one-off opacity (`Field`'s reveal icon, `GoogleButton`, `TextLink`, all
`0.82`). None of these fade a status colour against its own fill the way
Button's secondary variant does — they dim a muted icon or a link, which
has more headroom — but this was not verified numerically. Manual check:
hold each down under a screen magnifier or the OS's contrast-checking
accessibility tool and confirm the icon/text is still visibly a control.

## 5. Focus order and dialog/error announcements

**Audited and fixed.** `ErrorState` and `FormError` already announced
themselves correctly on mount and on text change
(`AccessibilityInfo.announceForAccessibility` plus
`accessibilityLiveRegion="assertive"` for Android's in-place case) — this
was the fix for an earlier, already-shipped bug and is covered by
`mobile/__tests__/announcements.test.tsx`.

`Dialog` had neither. Opening a `Modal` moves nothing onto it for either
VoiceOver or TalkBack by itself, so a dialog that appeared was one a screen
reader user did not know existed until they happened to swipe onto it.
Fixed: `Dialog` now announces its title (and message, if it has one) the
instant `visible` turns true, the same pattern `ErrorState`/`FormError`
already use. `accessibilityViewIsModal` (iOS) on the card was already
present and scopes swipe navigation to the dialog once VoiceOver does reach
it.

**Manual check (VoiceOver, iOS):**

1. Settings → Accessibility → VoiceOver → on.
2. Open the app, swipe through the Dashboard, History and Profile tabs.
   Confirm swiping right moves through the screen in the same order it
   reads top to bottom, left to right — nothing jumps or repeats.
3. Trigger a Dialog (Profile → Goal). Confirm VoiceOver speaks the title
   (and message) as soon as it opens, without having to swipe to find it,
   and that swiping while it is open stays inside the dialog rather than
   escaping to the screen behind it.
4. Trigger a field error (Login with a wrong password, or Register with a
   too-short password). Confirm it is spoken immediately, without moving
   focus there by hand.
5. Confirm every button and row still has a spoken label that names what it
   does, not just what it looks like (e.g. "Log again, button" rather than
   silence, or a bare icon name).

**Manual check (TalkBack, Android):**

1. Settings → Accessibility → TalkBack → on.
2. Repeat steps 2–5 above. TalkBack's "explore by touch" order and its
   linear swipe order can disagree in ways VoiceOver's usually does not, so
   check both: swipe through the whole screen, and separately drag a finger
   around it.
3. Confirm the same Dialog and FormError announcements are heard — Android
   is the platform `accessibilityLiveRegion="assertive"` exists for
   specifically, so this is worth checking even though it is also covered
   by an automated test.

## What is not yet covered

Two of the three audits requested alongside this one are their own, larger
pieces of work and are tracked separately rather than folded in here at low
quality:

- **Responsive layout** (a `useLayout()` breakpoint hook, a two-column
  tablet dashboard/history, 320dp and landscape verification, keyboard
  avoidance on Log/Login/Register) — not started.
- **Loading and empty states, swipe-to-delete with undo** (skeleton
  placeholders, `react-native-gesture-handler` swipe with a soft-undo
  snackbar and a non-gesture delete path) — not started.

When either lands, its own manual device checklist belongs in this file
alongside the sections above, not in a separate document.
